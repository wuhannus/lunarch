## 3. Formality Among the Three Versions — Architecture-Contract Level

Because the three RTL modules do not execute, netlist-level equivalence (e.g. Yosys
`equiv_*` / formal tools) is **not yet possible**. What is rigorous *and* meaningful
today is **ISA architecture-contract equivalence**, established by design:

| Comparison | Relation | Basis | Meaning |
|------------|----------|-------|---------|
| **v1 vs v1_sram** | **equivalent (≡)** | Same RV32IMC ISA; v1_sram only replaces DFF storage (regfile + caches) with sky130 SRAM macros | Identical instruction set & observable architecture; storage technology is an implementation detail |
| **v2 vs v1** | **superset (⊇)** | v2 = RV32IMC base + 11 agentic instructions (Xagentic 5, Xst 4, Xkv 2) | v2 must execute every v1 program with identical architectural state on the RV32IMC subset |
| **v1_sram vs v2** | **subset (⊂)** | Same reasoning transitivity: v1_sram ⊂ v2 | v1_sram programs run unchanged on v2's RV32IMC core |

**Verification requirement that must hold (gate for future):** run an identical
RV32IMC conformance corpus (RISCOF rv32i + rv32m + rv32c) on all three cores and
require **100% identical architectural state** (x0–x31, PC, CSRs) for every v1/v1_sram
program. v2 additionally requires its extension-corpus tests. This is the formal gate
that the earlier DFF-vs-SRAM "golden model" claim (100% ISA match) was based on — but
it must be re-run on compiling RTL to be trusted.

**What is runnable now:** the working `profile_cpu.py` RV32IMC emulator can serve as
the golden ISA reference for the shared-subset check.
